## 동작과 실행

앱에 들어오면 4초간 환영 화면을 보여준 뒤 입력 화면을 연다. “입력 확인”은 로컬 검증을 수행하며, 유효한 입력을 확인한 뒤 “다음”으로 기능 화면에 들어간다. 맞춤 추천·공고 탐색·진로 준비·관련 사이트 중 선택한 화면을 표시한다. “입력 수정”으로 돌아가면 입력을 유지하고, 입력을 바꾸면 다시 확인해야 한다. 추천이 활성화된 서버에는 “다음”을 누른 시점부터 요청한다.

기존 엔트리 화면의 health 및 개발 기능 목록을 사용자 입력 폼으로 교체했다. 기본 입력 네 가지 중 하나와 접을 수 있는 상세 입력을 지원한다. 활동을 추가하면 목록으로 상태를 결정하고, 마지막 활동을 삭제하면 미입력으로 돌아간다. 실제 활동이 없는 경우는 사용자가 따로 선택한다. 외부 AI 동의는 항상 false이고 브라우저 화면 메모리에만 프로필을 유지한다.

개발 서버에서 주소에 `?preview=1`을 붙이면 별도 테스트 모드로 열 수 있다. 고정 임시 응답으로 추천, 검색·저장, 진로 준비, 관련 사이트를 확인할 수 있다. 테스트 입력은 서버로 보내지 않고 저장한 예시 공고는 현재 화면 메모리에만 유지한다. 테스트 사이트와 공고는 화면 확인용이며 일반 URL은 실제 서버를 사용한다.

`VITE_API_BASE_URL`은 서버 origin만 받으며 기본값은 `http://localhost:8000`이다. 프론트 origin은 서버 CORS 설정과 일치시킨다. 설치와 가상환경 생성은 루트 README를 따른다.

```powershell
.venv\Scripts\python -m uvicorn backend.main:app --host 127.0.0.1 --port 8000 --no-access-log
# 별도 터미널
npm --prefix frontend run dev
```

기존 `options`로 분야 제안과 학적·활동 상태 선택지를 읽고, `capabilities`에서 해당 기능의 두 플래그가 모두 true일 때 생성 타입의 요청을 보낸다. 추천이 비활성 또는 확인 불가일 때 “입력 확인”은 로컬 검증이며 준비 상태를 안내한다. 실제 요청이 실패하면 오류를 표시한다. 브라우저의 API 응답 대체는 테스트에 사용한다. 입력 변경, 재요청 및 화면 해제는 이전 요청을 취소한다. 422, 503, 네트워크 오류와 서버 오류는 화면에서 별도로 안내한다.

관심 분야와 희망 직무는 서버 `options.fields`의 표시명·별칭 선택과 직접 입력을 지원한다. 희망 근무지는 서울·경기가 맨 앞인 17개 시·도 목록에서 복수로 선택한다. 고등학교 졸업은 학년을 받지 않고 서버의 기존 `graduated` 상태와 입력한 학교 이름을 전송한다. 자격증·영어시험은 기존 `other` 유형에 이름 접두사를 붙여 구분하고, 점수·등급 등은 설명으로 전송한다. 별도 학력 단계나 자격증·영어시험 전용 필드는 현재 공통 계약에 없다.

추천 성공 응답이 오면 목록과 상세를 표시한다. 관련성 점수, 지원 자격, 추천 이유, 주의사항을 구분한다. 상세에서는 공고 원문과 접수·행사·게시 일정을 볼 수 있다. 자격증 운영 상태와 시험 회차별 접수 상태는 별도로 표시한다. 실제 자료의 HTTP(S) 원문만 새 탭으로 열 수 있다.

맞춤 추천 화면에는 확인한 학적·전공·희망 직무·활동을 먼저 표시한다. 추천 응답은 자격증, 어학 요건, 인턴, 포트폴리오 활동, 연구·진학, 채용·기업, 학교·기관 공지, 설명회·박람회로 탐색할 수 있다. 연구·진학은 추천 결과의 제목·태그에 있는 학부연구생·연구 인턴·대학원 모집과 학위·연구 조건이 있는 공고를 표시한다. 어학, 자격증, 학위·연구 조건은 응답의 준비 요건 또는 지원 조건에 있는 문구를 그대로 표시한다. 기준 점수와 필수·우대 여부는 프론트에서 산정하지 않는다. 공지·행사 카드에는 서버가 제공한 게시일, 행사일, 접수 마감을 따로 표시한다.

공고 탐색에서 전체 공고, 학교·기관 공지, 설명회·박람회, 관심 공고를 볼 수 있다. 공고 API는 페이지 단위로 목록을 제공하므로 검색과 유형 필터는 불러온 목록에 적용된다. 관심 공고는 브라우저에 공고 ID만 저장하며 목록에 없는 경우 개별 조회할 수 있다. 프로필은 메모리에서 사용한다.

직무 설명, 다음 활동, 면접 준비는 검증된 입력을 각각의 API에 보내고, 관련 사이트는 별도 목록 API를 사용한다. 각 화면은 로딩·오류·재시도와 결과를 독립적으로 관리한다. 한 화면이 실패해도 다른 화면의 결과는 유지한다.

## 백엔드 인계

현재 공통 기반은 `options`와 `capabilities`를 제공한다. 실제 추천이 준비되려면 서버가 추천 처리와 공고 결합을 구현하여 `RecommendationApiResponse`를 반환하고, 각 기능의 enabled 및 implemented 상태를 함께 갱신해야 한다. 이후 실제 데이터로 추천·공고 상세·원문 이동과 후속 기능을 통합 검증한다.

현 계약에서 직무 응답은 ID와 설명을 제공하므로 화면에는 설명을 표시한다. 직무명이나 준비 역량을 별도 항목으로 표시하려면 직무 원본 또는 응답 필드가 필요하다. 학교 공지는 공개 공지 목록을 사용하며 학교별 자동 연결에는 학교와 공고를 연결하는 계약이 필요하다. 전체 목록 대상 서버 검색에는 검색어·유형 쿼리가 필요하다.

## PR #4 검토 반영

- 기준은 로컬과 원격 PR HEAD `b71c5d6` 및 `main` `cd8c0ca`다. 공개 추천 1차는 [PR #6](https://github.com/kkhee67/LOTUS/pull/6)의 `e3ebed9`를 별도로 추출해 실행했다. 미업로드 2차 코드는 검사 범위에 포함되지 않는다.
- 수정 전 390px Edge에서 드롭다운으로 `웹 개발자`를 선택한 요청과 `개발`을 직접 입력한 요청을 캡처했다. 두 요청을 동일한 소프트웨어 합성 공고로 추천 1차 함수에 넣은 결과 각각 0건, 1건(40점)이었다. 22:10 마감 공고는 시간을 22:11로 바꾼 뒤 상세를 펼쳐도 접수 중이었다.
- 관심·희망 직무 드롭다운은 `/options`의 분야 코드로 그룹을 식별하고, 표시명과 등록 별칭을 선택한 그대로 전송한다. 예를 들어 `software` 그룹은 `소프트웨어`, `개발`, `프로그래밍`을 제공한다. 목록 밖 직무명은 직접 입력할 수 있으며, 추천에서 인식되지 않을 수 있다는 안내를 표시한다.
- 수정 후 실제 `GET /options`의 표시명·별칭과 드롭다운을 대조했다. 390px Edge에서 목록의 `개발`, `소프트웨어`를 선택하고 `웹 개발자`를 직접 입력해 각각 실제 POST 본문을 캡처했다. 동일 공고와 공개 추천 함수에서 두 선택은 각각 1건(40점), 직접 입력은 원문 그대로 0건이었다. `frontend/tests/check_recommendation_engine.py`에 브라우저에서 캡처한 테스트 JSON 배열을 전달해 재검증할 수 있다.
- 접수 상태 계산은 기존 규칙을 사용한다. 공고 상세와 자격증 회차는 접수 시작, 정확한 마감, 서울 기준 날짜 마감 및 당일 안내 경계에 타이머를 예약한다. 탭 복귀와 창 포커스에서도 다시 계산하고, 데이터 변경·화면 해제 시 타이머와 이벤트를 정리한다. 390px Edge의 응답 대체 검사에서 추천·공고 탐색·관심 공고 각각 정확한 마감, 서울 자정 마감, 시험 회차가 조작 없이 갱신되는 것을 확인했다. 관심 공고는 탭 복귀 재계산도 확인했다.
- 실제 HTTP는 `GET /options` 200과 유효한 `POST /recommendations`의 `503 FEATURE_UNAVAILABLE`까지 확인했다. 브라우저 카드와 시간 이동 검사는 응답을 대체했고, 점수 비교는 공개 Python 추천 함수를 직접 실행했다. 성공 응답을 반환하는 실제 HTTP 어댑터 연결은 미검증이다.
- 협의 사항은 `웹 개발자`·`프론트엔드 개발자`를 소프트웨어 분야의 별칭으로 볼지, `UX/UI 디자이너`와 `데이터 엔지니어`처럼 세부 직무는 별도 직무로 다룰지다. 태환과 일치 기준 및 테스트 공고를 정한 뒤 건희와 `/options` 반영 범위를 맞춘다. 이 작업에서는 엔진, 카탈로그, 공통 타입을 수정하지 않았다.

## 공고 조회 활성화 후 프론트 후속 작업

- 로컬 브랜치 `codex/frontend/service-feedback`는 `main`의 `e01ce93`을 기준으로 한다. #7·#13은 포함되어 있고, 확인 시 #8은 `0138da6`이며 최신 main을 포함하지 않았다. 추천 성공·0건·오류·복구를 최신 통합 HTTP에서 검증하는 작업은 남아 있다. 현재 main에서는 추천을 요청하지 않는다.
- 기존 로컬 API `127.0.0.1:8100`은 health 200이지만 조회 기능이 비활성이고 목록은 503이었다. 별도 검증은 프론트 `http://127.0.0.1:15371`과 API origin `http://127.0.0.1:18371`을 사용했다. 해당 서버는 `opportunities`만 활성이다. 공유 DB와 기존 서버의 DB는 수정하지 않았다.
- 건희는 제공할 서버에서 최신 main을 실행하고, 지정한 SQLite 파일을 `DATABASE_URL=sqlite:///runtime/frontend-followup-real.db` 같은 설정으로 일관되게 가리키도록 한다. 실제 자료 환경은 `DATA_MODE=real`을 사용하고, 비어 있는 검증 DB에는 저장소 루트에서 `python -m backend.importer --input-dir data/normalized --mode real --database runtime/frontend-followup-real.db`로 실제 배치를 넣는다. `CORS_ORIGINS`에는 실제 프론트 origin을, 프론트의 `VITE_API_BASE_URL`에는 경로 없는 API origin을 설정한다.
- 비활성 기능은 capabilities를 기준으로 준비 상태를 표시하고 호출을 막는다. 상태 조회 실패에는 별도 연결 재시도가 있다. 활성 상태에서 받은 HTTP 503에는 일시 실패와 재시도를 안내한다. 공통 오류 코드 `FEATURE_UNAVAILABLE`로는 세부 원인을 구분할 수 없으므로 서버 메시지나 DB 원인을 추정해 표시하지 않는다. 정상 0건, 404, 네트워크 오류 처리는 각각 유지한다.
- 추천 결과의 분야별 표시 건수는 화면 목록을 기준으로 계산한다. `candidate_count`가 응답 `items`보다 크면 전체 후보 수와 받은 수를 별도로 안내한다.
- 시영에게 필요한 작업은 실제 공고·링크와 출처를 검증한 배치로 유지하는 것이다. 이번 검증은 기존 단국대 공고 3건을 사용했다. 태환·건희는 #8을 최신 main에 맞춘 뒤 실제 HTTP 추천과 결과 개수·근거·자격 표시를 함께 확인한다. 미업로드 추천 2·3차의 결과 수는 기대값으로 사용하지 않았다.
- 실제 FastAPI와 임시 real DB로 Edge 390px·1280px에서 목록 3건, 상세·원문 링크 주소, 관심 공고 ID 저장·새로고침 후 상세 재조회, 입력 초기화를 확인했다. 임시 DB에서 404·누락/모드 불일치 503과 복구 후 재시도 200, 정상 빈 목록 200을 확인하고 배치를 복원했다. 외부 원문 사이트의 접근과 최신성은 확인하지 않았다. 실제 배치의 시각 마감은 브라우저 시계로 경계를 넘겨 상세 자동 갱신과 visibilitychange 재계산을 검증했다. 날짜 전용 마감은 실제 배치에 없어 별도 합성 화면에서 서울 다음 날 자정을 검증했다.
- 타입 검사·테스트 25개·빌드·공백 검사 통과. 생성 타입 검사는 Windows 체크아웃에서 CRLF 때문에 실패했고 Git의 LF 원본 사본에 동일한 생성기 `--check`를 실행하면 통과한다.
